# 幻灯片编写指南

我们是一家基础软件公司的技术洞察组。
胶片一定要有“逻辑”：这里的逻辑通常是一个 *故事*，看上去讲得通、讲得顺。胶片不是信息的简单罗列：既要有客观事实，也要给出趋势观点。

## 出片硬门槛

这是验收条件，不是写作建议。任何一条没过，就不算完成。

1. 每页标题是观点句，不是主题词。
2. 每个框标题是观点，不是文件名、路径或命令名，也不能只是产品名。
3. 启示一行、50 字以内，前半句 so what，后半句 now what。
4. 同一 section 只用一种 card 或 frame 变体。
5. card 页和 frame 页的纵向几何符合模板坐标。
6. 正文不小于 12.5pt；来源 10.5pt 灰色斜体、完整 URL、在本框内。
7. 没有 `·`、`「」`、`『』`、`——`；中文和英文/数字之间没有空格。
8. `accent` 只落在比较句或因果句的数字上，不标 `1cm`、`14pt` 这类孤立单位。
9. 封面只有 title 和 author，结尾页只有 master。
10. 图片按原始像素比例缩放。
11. 跑完本文件末尾的“机械检查”命令块，全部通过。
12. 预览图逐页看过；同一块布局两轮没修好就整块重排。

排版反例见 [`references/anti-patterns.md`](references/anti-patterns.md)。

## 调研

留住调研过程，而不只是最后的胶片。每个上到胶片上的事实，都应该能追溯到你写下来的东西。
比如洞察一个软件，你需要了解它背后的作者、推手是谁。对于开源软件你需要通过 star-history 看社区热度怎么样，必要的时候把代码仓拉下来分析分析。

- **`references/` 是事实来源。** 上网检索时，把查到的东西写进项目 `references/` 下的 Markdown 文件：链接、原文摘录、日期、你提取的数字，并在每个文件开头写清楚当时要回答的问题。链接要写成能直接点开的完整 URL，不能只写“来自某某报告”或“某某博客”：读者得能自己点进去核对。写胶片时依据这些文件，而不是凭记忆：后来的人必须能重新核对某个说法，而不必重做一遍检索。调研的代码仓也可以拉到这个目录下，总之这是个原始信息的存放目录。机制术语（恢复/映射/COW vs 克隆/拷贝）也要先找原话，摘进 `references/`。
- **`references/media/` 存放原始素材。** 调研中收集的截图、示意图、图表放在这里，并在引用它的 Markdown 文件里记录出处。
- **`media/` 只放最终要用的东西。** 只有当某页胶片真正用到某个素材时，才把它复制进 `media/`，这样构建就不依赖项目之外的任何文件。

注意：这些是项目的路径，不是本 skill 的路径：本文件旁边的 `references/` 放的是排版示例，不是调研资料。

## 文件与命名

胶片会反复增删和调序，文件名不能承担顺序。

- **不要用数字或顺序前缀命名。** `01-`、`1-`、`v2-`、`step1-` 这类前缀会立刻过期：中间插一页就出现 `02a`，删一页就留下空号，调序就得批量改名。
- **用内容命名。** `pptx-format.toml`、`why-toml.toml`、`progress-2026.md`：读文件名就知道这页讲什么。
- **顺序只有一个来源：`main.toml` 的 `sections.slides`。** 调序只改这个列表，文件名不动；新增页也一样，加文件、改列表。
- `references/` 同样不用编号，文件的一级标题也不要写“03 为什么选 TOML”，直接写“为什么选 TOML”。
- 例外：`media/` 下的素材保留来源侧原名，方便回溯出处。

## 整体结构

一个完整胶片通常包含封面页、章节页和结束页。

结构遵循“总-分-总”。章节页按作用分为三类：

- **帽子页**：接下来几页的总起页，一般每个章节前有一个。
- **内容页**：论证的主体。
- **启示页**：对前面内容的总结启示，通常在结束页之前有一个总启示页。

另外两条边界：

- **封面和结尾回到模板。** 封面只放 title 和 author 两个 placeholder，不要加副标题、日期、金句或装饰色块；结尾页只写 `master = "end"`，不加“谢谢”“Q&A”。
- **10 页以内不加章节页。** 用顶部导航代替章节页，把版面留给内容。

## 单页胶片的写法

单页胶片由三部分组成：**标题**、**正文**和**启示**。

一页从选题到打磨通常是五步：**选题 → 逻辑 → 结构 → 版面 → 打磨**。其中逻辑是核心：每页只能有一条，标题是它的观点，正文是它的证据，启示是它的落点。见 [`references/phase-evolution.toml`](references/phase-evolution.toml)。

排版默认：字体 `Microsoft YaHei`。数字/英文和汉字之间不要加空格。避免 `·`、`「」`、`『』`、`——` 这类明显像 AI 生成的标点。正文、启示和列表项结尾不加句号；问号和感叹号保留。

### 标题即观点

标题必须直接给出观点，通常是“一个现象 + 这个现象意味着什么”。主题词不是标题。

- 反例：《NV G3.5技术介绍》
  - 点评：这只是一个主题词。读者扫一眼标题得不到任何信息，而很多人只看标题：标题不行，这页上来就废了。
- 正例：《NV新增G3.5层，GPU直连远端存储加速推理，长上下文Agent负载TPS 5×↑》
  - 点评：它点出现象（“NV新增G3.5层”），用一句话解释新名词（GPU直连远端存储、加速推理），再说清它意味着什么、价值多大。能量化就量化（“TPS5×↑”“成本50%↓”）。

量化时方向符号始终放在数字后面：**快5×↑**、**成本50%↓**，不要写成“快5倍”“↓50%”。关键数字用模板里的 `accent` 命名样式标红加粗：`快<span class="accent">5×↑</span>`。

标题默认样式：24pt 红色（`C7000A`）加粗、左对齐，位于胶片顶部，尽量控制在一行。

### 正文

正文灵活且信息量大，但一定要有逻辑，且每页只能有一个逻辑。常见逻辑有：

- **Bad → Good**：左边讲现状（AS-IS / 别人 / ……）是什么、有什么问题，右边讲更好的状态（TO-BE / 我们 / ……）是什么、价值在哪；中间用模板的双三角箭头 `media/two-triangles-right-arrow.svg` 连接，或者自己画一个灰色箭头，大小自定。见 [`references/frames.toml`](references/frames.toml)。
- **分阶段演进**：给出各阶段的特点和典型代表，下面再导出各阶段的诉求，最后是未来趋势。见 [`references/phase-evolution.toml`](references/phase-evolution.toml) 和 [`references/cards.toml`](references/cards.toml)。
- **总-分**：左边讲一个大逻辑，右边展开成几个小逻辑。例如左边是一个 AS-IS → TO-BE，右边讲它带来的两三个技术趋势；或者左边画一个软件栈，在上面用红色标几个关键点（`➊➋➌...`），右边展开讲这几个点。总-分常用的素材是 `media/perspective-floor.svg`，它朝细节方向“打开”，梯形**长边朝向细节**、**短边朝向总述一侧**；它很适合用作栈图和右侧注释列之间的视觉分隔。
- **分类**：按某种维度拆成不超过三个相对独立的小逻辑，每个逻辑块讲自己的故事。

正文写句子，每条至少是“做了什么 + 所以怎样”，不要堆名词短语（“GPU、CNCF、快照恢复”）；读者要能顺着句子读出因果。

正文具体怎么写要具体分析，下面是一些常用的组件：

- **五边形 + V 形箭头组合**：用于分阶段演进，放在页面上半部分；下方按阶段列出各自的特点和诉求。
- **阶梯**：用于分阶段演进。
- **小标题 + 内容框**，两种变体：
  - 等宽卡片（card）：小标题黑色加粗、居中，放在无边框的 `#ccecff` 框里，`card_title` 与 `card` 等宽；内容框 `#f2f2f2` 填充、无边框。使用命名样式 `card_title` / `card`（定义在模板的 `main.toml` 里）。见 [`references/cards.toml`](references/cards.toml)。
  - 小标题骑在内容顶边（frame）：标题 `#0000ff` 加粗、白色填充、无边框、居中，骑在圆角矩形（`rect_radius` 0.1）的顶边上，矩形 `#d3d3d3` 边框、白色填充。`frame_title` 要比 `frame` 窄，宽度按标题内容定，别拉得太宽留一片空白。使用命名样式 `frame` / `frame_title`。见 [`references/frames.toml`](references/frames.toml)。
  注意：
  - **变体按 section 定，不按页定。** 一个 section 内所有页固定用同一种变体，跨 section 再换。写第一节第一页时就把变体定下来，后面同 section 的页只能跟随，不能翻案：逐页交替会让整套看起来像没设计过。某页确实不适合当前变体时，换的是这页的内容组织方式（表格、栈图），不是换变体。
  - **小标题地位仅次于标题和启示，同样必须是观点，不能只是关键词**。
  - **框标题要过“单独读”测试。** 把它从页面上拿下来单独读，读者能不能得到一个判断？只能读到名词（`TOML`、`writer.rs`、`gwen build`、`02-trends.toml`）就不合格，重写成“动作 + 结果”。
  - **frame title 带上主体。** 技术方案类的框标题写明机构或产品，例如“谷歌开源gVisor”“清华&蚂蚁SKernel”，读者先知道是谁家的方案，再看判断。
- **表格**：表格呈现的逻辑要简单，一般在一个维度上比较两三个类别。用 `line` 形状画线、用 `text` 形状填格子（不加表头底色、不加竖线、格内边距要小），大小控制在约四分之一页，通常放在内容框做直观对比或证据支撑。不要一张表独占一页。见 [`references/frames.toml`](references/frames.toml) 的第三个框。
- **矩形框图**：这是读者最喜欢的展现形式，几乎每个软件项目的介绍都要画软件栈或架构图。架构图要分层，每层写清里面的关键组件；跨层的 sidecar 单独画出，组件之间的关系必要时用连线说明：“三个摞在一起的矩形”不叫架构图。不要面面俱到，只写关键组件，次要的用灰色小字或干脆不写。关键组件标清楚了，才能准确说明关键技术落在哪里，再按“总-分”在右侧展开这些点。见 [`references/stack.toml`](references/stack.toml)。
  - **先定层级语义，再摆框。** 层级可以是接入 / 运行时 / 基础设施，也可以是客户端 / 服务 / 存储；同一页的对照图必须使用同一套层级语言，不能左边三层、右边两层。
  - **执行路径和 I/O 路径分开画。** 中间层只承载它实际承载的路径，不要把两侧所有交互都塞进中间层。
  - **边界归属要清楚。** 权限、凭证、策略属于边界外就画在边界外，不要塞进被隔离对象内部；sidecar 单独画。同一页的对照图，一张画了控制面，另一张也要画，否则都不画。
  - **等宽、低信息层用扁框。** 同一组组件尽量等宽；只有一个标签的层不要拉成大空框。
  - **连线和图层。** 连线画在容器之后，避免被填充遮住；线要到达目标框边缘，箭头不能被框盖住。
  - **标签不用 `·` 分隔。** 用 `/` 或换行。

### 启示即观点

启示在胶片底部，是整页的落点。很多读者只看标题和启示，所以它值得和标题一样仔细斟酌。

启示通常包含两部分：**so what** 和 **now what**：前半句总结趋势，后半句给出方向建议。

启示默认样式：16pt 蓝色（`#0000ff`）加粗、水平居中，最好只有一行、50 字以内。

### 布局原则

- **平衡与对称。** 拿胶片尺寸把几何算清楚：13.34 x 7.5in 的胶片是 33.88 x 19.05cm，水平中线在 16.94cm，内容区大约 2.7–15.9cm（启示在 ~16.25cm）。优先用对称的两栏，例如左栏 `x = 1.5cm, w = 15cm`、右栏 `x = 17.4cm, w = 15cm`，两边留白互为镜像。歪掉的布局看起来就像没做完。
- **纵向坐标照模板抄。** 内容带要从标题下面开始、撑到启示上面，不要只占上半页：
  - card 页：标题条 `y = 2.95cm, h = 0.75cm`；`card_title` 与 `card` 同顶 `y = 3.7cm`，`card_title` 高 0.75cm，`card` 高 11.45cm；启示 `y = 16.25cm`。
  - frame 页：`frame_title` `y = 3.15cm`，`frame` `y = 3.6cm, h = 11.55cm`；启示 `y = 16.25cm`。
  - 内容底边离启示带超过 1.2cm 就是头重脚轻：把内容撑满或删掉一行，不要靠加空白解决。
- **文字留内边距。** 任何带文字的图形都需要内边距，别让文字贴边；默认是 `margin = ["0.13cm", "0.25cm", "0.13cm", "0.25cm"]`（上/右/下/左）。如果要把文字精确放到某个位置，就拆开：一个 `rect` 只画边框（不放文字），再单独放一个 `text` 形状自己定位。
- **正文与标号。** 同一块正文只用一个 `text`，换行用 `<br>`，不要拆成多个文本框；性能数据默认并入最后一行（同框 12pt `data` span），只有独立对照表才拆。正文标号内联用 `<span class="marker">➊</span>`/`<span class="marker">🅐</span>`，图上标位置仍单独放；标号统一用 `marker` 样式（红色不加粗），`accent` 只给关键数字/结论。
- **标签框按行高留够。** 12pt 标签框高度至少 0.45cm，14pt 至少 0.55cm；标签和下一个框留 0.05–0.1cm，避免文字下半截被后画的框盖住。
- **标题与 logo。** logo 与标题条同高、保持原始比例；`frame_title` 左对齐贴 logo，`card_title` 用默认居中，不要为了贴 logo 改 `align`/宽度或手算文字位置。标题文字设 `fill = none`，避免盖住 logo；缺 logo 优先官方 assets/wordmark，其次组织头像并注明来源。
- **来源放进对应 frame。** 每条来源放各自 frame 内，左右来源对齐同一基线；不要合并成一条跨两栏的来源线。
- **缩图要整组缩。** 缩窄架构图时，x 坐标、内部框、标签、连线通道一起缩放，不能只改一个框。
- **数字不要充门面。** 不要用超大字号把单个数字做成视觉冲击；我们做的是洞察，不是宣传。数字是证据，放进比较或因果句里，字号与正文同级，需要强调时靠加粗红/蓝。测试：把这个数字删掉，句子还成立吗？成立就说明它只是装饰，删掉。

正文默认 14pt；重要部分加粗红/蓝。来源是 10.5pt 灰色斜体（`#a3a3a3`，`source` 样式），写完整链接，不要只写机构名或“内部资料”。颜色要少：黑、白、红、蓝、灰，其中红蓝只用于标题、启示和强调，慎用。

我们的胶片信息密度很高，不要留明显的空白。出片后先看预览图，版面问题在图上最直观。

```sh
gwen build  <项目>            # 生成 target/<标题>.pptx
gwen render <项目>            # 预览 PNG 写到 target/render/
gwen render <项目> --page 4   # 只看一页
```

但也不要为了写而写，正文是为了支撑标题和启示里的观点：每一项都要和页面其他内容形成逻辑，没有关联的无效信息很容易被围攻。

用户改过的文案默认视为定稿；只调版式，不改词。版式返工轮次里，标题、正文、启示都是只读的；要改词先单独提出来确认，不要夹在排版改动里。画图指令（2×2、居中、省略号）只落到图，不要写进正文。

## 检查

一页什么时候算写完：逻辑严密（内容）、布局美观（形式）。

### 内容逻辑严密

阅读顺序是读者走完这页的唯一路径。每次修改后，从上到下通读整套胶片，检查三层：

- **句子。** 每句话是否由上一句自然推出？一个观点需要它的证据就在手边。
- **页面。** 每个元素是否都在服务标题？正文是否落到启示上？不承载这条线的东西，要么删掉要么挪走，不要靠装饰救。
- **整套。** 各页是否按总-分-总层层推进，没有重复、没有互相矛盾？

逻辑上重点抓这些毛病：

- **前后矛盾。** 同一个数字、名字或观点，在每一页、每一份资料里都必须是同一个意思。如果两页打架，必有一页是错的。
- **埋了不兑现的伏笔。** 要么展开，要么删掉。你提到却从不展开的术语、例子或问题，会让读者一直等着；提了不兑现，比不提更糟。生僻术语第一次出现时，先用几个字定义清楚，再拿它论证。
- **过分夸大。** 收集到的信息普遍都会“王婆卖瓜”，但你要站在一个客观中立的立场上，严肃地做逻辑推导。
- **不要把能力当成独家。** 写“某产品有某能力”前先验证替代方案，不要把架构事实直接写成竞品做不到；区分产品差异化和通用能力。
- **数字要交代口径。** 微基准、生产实测、厂商博客是三种证据，不能并排摆着当成一类；旧数据必须带年份，别把 2019 年的覆盖率当现状。
- **案例和机制一页讲透。** 同一套机制或同一个案例，整套里只在一页展开；别的页只引用结论，不复述图和数字。写新面板前先搜一遍整套胶片，确认没和别的页撞车。

另外要杜绝 AI 味，讲人话，禁止使用“不是……而是……”。

反复检查修改直到自己认为达到满分为止，每一句、每一页和整套胶片的逻辑都是打磨出来的，不是写出来的。

### 形式布局美观

`gwen render` 出的预览图里找空，眼睛找碰撞、溢出和断行；两项都过了才算排版完成。

- **对称与边距。** 两栏的宽度、间距、上下留白互为镜像；内容落在 2.7–15.9cm 内，启示带不挤到页脚。
- **对齐。** 同类元素共用基准线：卡片顶端、卡片宽度、文字左边界、标题与框的中心线。不要出现差 0.1cm 的“差不多”。
- **重叠。** 检查文字是否压住边框、箭头是否穿进卡片、注释是否盖住图形。
- **图层顺序。** 填充容器是否盖住连线或箭头；线是否真的到达目标框，而不是停在容器边缘。
- **放大看局部。** 先看整页，再放大或裁切检查标签、线、箭头、标题与 logo；不要只验坐标。
- **两振出局。** 同一块布局连续两轮返工仍有碰撞、空洞或断行，停止微调，整块重排：改行数、改分栏、改字号。逐次挪 0.1cm 是最贵的做法，既看不出进展也改不干净。
- **溢出。** 文字是否超出框、被裁切或自动缩小；表格和栈图是否顶到安全边距。
- **断行。** 标题是否被迫折行、卡片里是否出现孤字或单词被拆开；改字号或改文案，不要硬塞。
- **文本块完整。** 一段正文有没有被拆成好几个文本框；能合并的合并，断行靠 `<br>`，标记内联。
- **颜色。** 全页是否只有黑、白、灰，红蓝只落在标题、启示和关键数字上；没有装饰性色块或渐变。
- **密度。** 远离边缘的大空洞要填，明显比同套稀疏的页要补，但不要靠塞废话充数。
- **一致性。** 卡片样式、圆角、线宽、字号层级、箭头形态保持一套；同一 section 只用一种变体；导航 active 必须和 `main.toml` 的 section 一致。

### 机械检查

能机械判定的不要靠眼睛。每次改完跑这一组，负向检查没有输出才算通过（`rg` 无匹配时退出码是 1，属于正常）：

```sh
gwen fmt <项目> --check
gwen build <项目>
gwen render <项目> && gwen render <项目> --html

rg -n '·|「|」|『|』|——' slides references
# 只看形状文案，开头的 notes 块不参与排版
rg -nP '^\s*text\s*=\s*".*([\p{Han}]\s+[A-Za-z0-9]|[A-Za-z0-9]\s+[\p{Han}])' slides
rg -n 'class="accent">[0-9.]+(cm|pt|in|em|px)<' slides
ls slides references | rg '^[0-9]+[-_]'
rg -c '^\[\[shapes\]\]' slides/cover.toml   # 2 个 placeholder
rg -c '^\[\[shapes\]\]' slides/end.toml     # 0 个形状
```

`gwen build` 已经会拦截 TOML 语法、未知字段、样式引用和类型错误，不要重复检查这些。机械检查只兜住 gwen 不管的文案与几何约定。项目多了或规则变复杂再考虑写脚本，别为几条 `rg` 建 `scripts/`。

剩下三条只能人看，别指望命令：同一 section 的变体是否一致（对着 `main.toml` 逐页扫一遍 `styles`）、图片有没有变形、来源是不是落在各自的框里。
