# 幻灯片编写指南

我们是一家基础软件公司的技术洞察组。
胶片要有“逻辑”：逻辑通常是一个 *故事*，看上去讲得通、讲得顺。胶片不是信息罗列：既要有客观事实，也要给出趋势观点。

## 出片硬门槛

这是验收条件，不是写作建议。任何一条没过，就不算完成。

1. 每页标题 = 主体 + 判断/价值：主体唯一；有数据讲价值，没数据讲判断。
2. 每个框标题同样有主体和判断/价值，不能是文件名、路径或命令名。
3. 启示一行、50 字以内，前半句 so what，后半句 now what。
4. 同一 section 只用一种 card 或 frame 变体。
5. 正文 14pt；来源 10.5pt 灰色斜体。
6. 没有 `·`、`「」`、`『』`、`——`；中文和英文/数字之间没有空格；句尾不加句号。
7. `accent` 只落在比较句或因果句的数字上。
8. 封面只有 title 和 author，结尾页只有 master。
9. 图片按原始像素比例缩放。
10. `gwen fmt`、`build`、`render` 通过，预览逐页看过。
11. 有 `STORY.md`，且与 `slides/` 的章节顺序、每页结论一致。

常见返工见 [`references/anti-patterns.md`](references/anti-patterns.md)，写新页前扫一遍。

## 调研

留住调研过程，不只留最终胶片：每个上片的事实都要能追溯。

- **`references/` 是事实来源。** 把检索结果写进项目 `references/` 的 Markdown：要回答的问题、链接、原文摘录、日期、提取的数字。链接写完整 URL，让后来的人能直接核对，不必重做检索；机制术语先摘原话。代码仓也可以拉到这里。
- **`references/media/` 存原始素材。** 截图、示意图、图表放这里，并在引用它的 Markdown 里记出处。
- **`media/` 只放最终素材。** 某页真正用到时才复制进来，构建不依赖项目外的文件。

本文件旁边的 `references/` 是排版示例，不是调研资料。

## 文件与命名

胶片会反复增删调序，文件名不能承担顺序。

- **不用数字或顺序前缀。** `01-`、`1-`、`v2-`、`step1-` 会立刻过期：插一页出现 `02a`，删一页留下空号，调序要批量改名。
- **用内容命名。** `pptx-format.toml`、`why-toml.toml`：读名字就知道这页讲什么。
- **顺序只有一个来源：`main.toml` 的 `sections.slides`。** 调序、加页都只改这个列表。
- `references/` 的文件名和一级标题也不编号：写 `community-growth.md` 和「社区热度」，不写 `03-community-growth.md` 和「03 社区热度」。
- `media/` 保留来源侧原名，方便回溯。

## 整体结构

完整胶片通常有封面、章节、结束页，按“总-分-总”推进。章节页分三类：

- **帽子页**：章节总起，一般每节一个。
- **内容页**：论证主体。
- **启示页**：总结前文，通常在结束页前设一个总启示页。

两条边界：

- **封面和结尾回模板。** 封面只放 title 和 author，不加副标题、日期、金句或色块；结尾只写 `master = "end"`，不加“谢谢”“Q&A”。
- **10 页以内不加章节页。** 用顶部导航代替，把版面留给内容。

## 先写 STORY.md

正式写 TOML 前，先在项目根目录写 `STORY.md`，与 `references/` 并列。它只记逻辑，不记排版：

- **整体逻辑。** 一句话说明整套要证明什么、按什么顺序推进。
- **章节逻辑。** 每个 section 回答哪个问题，前后如何衔接。
- **每页逻辑。** 每页一行：主体、判断或价值、正文证据、启示落点。

`main.toml` 仍是构建顺序的唯一来源；`STORY.md` 必须和它、和 `slides/` 保持一致。改逻辑先改 `STORY.md`，再改 TOML，写完一页回头核对。缺事实、缺结论或叙事方向不明确时，先问用户，不要自己替用户定方向。

## 单页的写法

单页 = 标题 + 正文 + 启示：标题给判断或价值，正文是证据，启示是落点。
一页通常走五步：**选题 → 逻辑 → 结构 → 版面 → 打磨**，其中逻辑是核心，每页只有一条。见 [`references/phase-evolution.toml`](references/phase-evolution.toml)。

所有文字都用正向逻辑：不写三段排比、二元对仗，不用“不是……而是……”，不喊口号（“就是、才是、正是”）。

### 标题 = 主体 + 判断 / 价值

每个标题必须同时满足两条：

- **主体唯一，也是整页的主体。** 判断真正指向的那个东西，只能是公司、产品、技术方案或场景。正文、框标题和启示都在讲它，不能中途换主体或互相冲突。发布方、厂商名只是背景，不是主体；文件名、路径、命令、模块名更不能当主语。
- **判断或价值。** 有量化数据时直接讲价值：带来多少提升、省下多少成本。没有量化数据时讲自己的判断：这意味着什么、会走向哪。两者都不复述方案，也不做纯机制说明；数字要有出处、交代口径，判断要能被正文的证据撑住。

标题不写问句、选择句、清单或纯机制说明；标题不是摘要，不要把 card/frame 里的信息重抄一遍，也不要在冒号后面枚举。

写完做三个测试：

1. **单读。** 只看标题、不看正文，能不能立刻拿到观点？
2. **换页。** 把标题放到另一页也成立，说明太泛，重写。
3. **回看。** 主体是否唯一？正文、框标题和启示是否都在讲这个主体？讲的是判断还是价值？有没有证据？

每页先写两三个候选，再选最优。

- 反例：《NV G3.5技术介绍》：只有主题词，没有判断或价值。
- 反例：《我们为什么需要 G3.5？》：问句，读者拿不到结论。
- 正例：《NV新增G3.5层，GPU直连远端存储加速推理，长上下文Agent负载TPS 5×↑》：主体是 G3.5 层；价值是 GPU 直连远端存储带来的 TPS 5×↑。

量化时方向符号始终在数字后面：**快5×↑**、**成本50%↓**，不写“快5倍”“↓50%”。关键数字用 `accent` 标红加粗：`快<span class="accent">5×↑</span>`。

### 正文

正文信息量大，但每页只能有一个逻辑。常见逻辑：

- **Bad → Good**：左边讲现状（AS-IS / 别人）的问题，右边讲更好的状态（TO-BE / 我们）和价值；中间用双三角箭头 `media/two-triangles-right-arrow.svg` 或自画灰色箭头。见 [`references/frames.toml`](references/frames.toml)。
- **分阶段演进**：各阶段的特点和代表 → 诉求 → 趋势。上半页用五边形 + V 形箭头或阶梯，下方按阶段列要点。见 [`references/phase-evolution.toml`](references/phase-evolution.toml) 和 [`references/cards.toml`](references/cards.toml)。
- **总-分**：左边一个大逻辑，右边展开两三个小逻辑；例如左 AS-IS → TO-BE、右讲趋势，或左画栈图、右边用 `➊➋➌` 展开关键点。`media/perspective-floor.svg` 适合做分隔，梯形**长边朝细节、短边朝总述**。
- **分类**：按一个维度拆成不超过三个独立小逻辑。

正文写句子，每条至少是“做了什么 + 所以怎样”，不要堆名词短语；读者要能顺着句子读出因果。

常用组件：

- **小标题 + 内容框**，两种变体：
  - **card**：小标题黑色加粗、居中，放在无边框 `#ccecff` 框里，与内容框等宽；内容框 `#f2f2f2`、无边框。用 `card_title` / `card`。见 [`references/cards.toml`](references/cards.toml)。
  - **frame**：标题 `#0000ff` 加粗、白底、居中，骑在圆角矩形（`rect_radius` 0.1）顶边；矩形 `#d3d3d3` 边框、白底。`frame_title` 按标题内容定宽，别留一片空白。用 `frame` / `frame_title`。见 [`references/frames.toml`](references/frames.toml)。
  - **变体按 section 定，不按页定。** 一个 section 固定一种，跨 section 再换；写第一节第一页时就定下来，后面跟随。某页不适合当前变体时，换内容组织方式（表格、栈图），不是换变体。
  - **框标题按同一标准写。** 主体 + 判断/价值，单独读要能得出判断；主体不能是文件名，只能是公司、产品或方案。技术方案带上主体，例如“谷歌开源gVisor”。
- **表格**：在一个维度上比较两三个类别。用 `line` 画线、`text` 填格，不加表头底色和竖线，格内边距要小；控制在四分之一页，放进内容框做证据，不要独占一页。见 [`references/frames.toml`](references/frames.toml) 的第三个框。
- **矩形框图**：软件栈、架构图几乎每套都有。要分层，每层写关键组件；跨层 sidecar 单独画，关系用连线说明。不要面面俱到，次要组件用灰色小字或省略。见 [`references/stack.toml`](references/stack.toml)。
  - **先定层级语义。** 接入 / 运行时 / 基础设施，或客户端 / 服务 / 存储；同一页的对照图必须同一套，不能左边三层右边两层。
  - **执行路径和 I/O 路径分开画。** 中间层只承载它实际承载的路径。
  - **边界归属清楚。** 权限、凭证、策略属于边界外就画在边界外；sidecar 单独画。对照图要么都画控制面，要么都不画。
  - **等宽、低信息层用扁框。** 只有一个标签的层不要拉成大空框。
  - **连线和图层。** 线画在容器之后，避免被填充遮住；线要到达目标框边缘。标签不用 `·`，用 `/` 或换行。

但也不要为了写而写：正文要支撑标题和启示，每一项都要和页面其他内容形成逻辑，无关信息很容易被围攻。

### 启示即观点

启示在胶片底部，是整页落点。很多人只看标题和启示，所以要像标题一样斟酌。

启示包含 **so what** 和 **now what**：前半句总结趋势，后半句给出方向建议。最好一行、50 字以内。

### 布局原则

- **平衡与对称。** 胶片是 33.88 x 19.05cm，水平中线 16.94cm，内容区约 2.7–15.9cm（启示在 ~16.25cm）。优先对称两栏，例如左 `x = 1.5cm, w = 15cm`、右 `x = 17.4cm, w = 15cm`，留白互为镜像。
- **纵向坐标照模板抄。** 内容要从标题下撑到启示上：
  - card 页：标题条 `y = 2.95cm, h = 0.75cm`；`card_title` 与 `card` 同顶 `y = 3.7cm`，高 0.75 / 11.45cm；启示 `y = 16.25cm`。
  - frame 页：`frame_title` `y = 3.15cm`，`frame` `y = 3.6cm, h = 11.55cm`；启示 `y = 16.25cm`。
  - 内容底边离启示超过 1.2cm 就是头重脚轻：撑满或删一行，不要加空白。
- **文字留内边距。** 默认 `margin = ["0.13cm", "0.25cm", "0.13cm", "0.25cm"]`（上/右/下/左）。要精确定位就拆开：`rect` 只画边框，另放 `text` 自己定位。
- **正文与标号。** 一块正文只用一个 `text`，换行用 `<br>`；性能数据并入最后一行，强调用 `accent`。标号内联用 `<span class="marker">➊</span>`，图上位置仍单独放；统一用 `marker`（红色不加粗）。
- **标签框按行高留够。** 14pt 标签框至少 0.55cm；和下一个框留 0.05–0.1cm，避免下半截被盖住。
- **标题与 logo。** logo 与标题条同高、保持比例；`frame_title` 左贴 logo，`card_title` 默认居中，不为贴 logo 改 `align` 或手算位置。标题设 `fill = none`，避免盖住 logo；缺 logo 优先官方 wordmark，其次组织头像并注明来源。
- **来源放进对应 frame。** 每条来源放各自框内，左右对齐同一基线；不要合并成跨栏来源线。用 `source` 样式，写完整 URL，不只写机构名或“内部资料”。
- **缩图要整组缩。** x 坐标、内部框、标签、连线通道一起缩放，不能只改一个框。
- **数字不要充门面。** 不要用超大字号做视觉冲击；数字是证据，放进比较或因果句，字号同正文，强调靠加粗红/蓝。删掉这个数字句子还成立，说明它只是装饰。

排版约定：页标题 24pt 红色加粗、左对齐、尽量一行；启示 16pt 蓝色加粗、居中；正文 14pt；来源 10.5pt 灰色斜体。颜色只用黑、白、红、蓝、灰，红蓝只给标题、小标题、启示和关键数字。

胶片信息密度很高，不要留明显的空白。

### 协作

用户改过的文案默认是定稿：只调版式，不改词。版式返工轮次里标题、正文、启示只读；要改词先单独确认。画图指令（2×2、居中、省略号）只落图，不写进正文。

## 检查

一页算写完：逻辑严密（内容）、布局美观（形式）。

### 内容逻辑严密

阅读顺序是读者走完这页的唯一路径。每次修改后从上到下通读整套，检查三层：

- **句子。** 每句话是否由上一句自然推出？观点的证据是否在手边。
- **页面。** 每个元素是否服务标题、是否围绕同一个主体？正文是否落到启示？不承载这条线的东西，删掉或挪走。
- **整套。** 是否按总-分-总推进，`STORY.md` 与 `slides/` 的章节顺序、每页结论是否一致，没有重复、没有矛盾。

重点抓这些毛病：

- **前后矛盾。** 同一个数字、名字或观点，每页、每份资料里必须是同一个意思。两页打架，必有一页是错的。
- **埋了不兑现的伏笔。** 提到就要展开，否则删掉；生僻术语第一次出现先定义。提了不兑现比不提更糟。
- **过分夸大。** 信息源普遍“王婆卖瓜”，你要站客观中立立场做推导。
- **不要把能力当独家。** 写“某产品有某能力”前先验证替代方案，区分产品差异化和通用能力。
- **数字要交代口径。** 微基准、生产实测、厂商博客是三种证据，不能当成一类；旧数据带年份。
- **案例和机制一页讲透。** 同一机制或案例整套只在一页展开，其他页只引结论。写新页前先搜整套，确认没撞车。

通读时删掉 AI 味：排比、对仗、二元对立、口号式连接词。

反复修改到满分：每一句、每一页和整套的逻辑都是打磨出来的。

### 形式布局美观

`gwen render` 后逐页看，按这个顺序：

- **整页。** 两栏留白是否镜像；内容带是否撑到启示带；有没有远离边缘的大空洞。
- **放大。** 文字压边框、箭头穿卡片、注释盖图形、连线被填充遮住。
- **局部。** 标题或标签断行、文字溢出或自动缩小、图片变形、来源是否在本框。
- **一致。** 同一 section 的变体、圆角、线宽、字号层级、箭头形态；导航 active 和 `main.toml` 一致。
- **两振出局。** 同一块布局两轮仍碰撞、空洞或断行，停止微调，整块重排：改行数、改分栏、改字号。

### 机械检查

能机械判定的不要靠眼睛。每次改完跑这一组，负向检查没有输出才算通过（`rg` 无匹配时退出码是 1，正常）：

```sh
gwen fmt <项目> --check
gwen build <项目>
gwen render <项目> && gwen render <项目> --html

rg -n '·|「|」|『|』|——' slides references
# 只看形状文案，开头的 notes 块不参与排版
rg -nP '^\s*text\s*=\s*".*([\p{Han}]\s+[A-Za-z0-9]|[A-Za-z0-9]\s+[\p{Han}])' slides
rg -n 'class="accent">[0-9.]+(cm|pt|in|em|px)<' slides
ls slides references | rg '^[0-9]+[-_]'
rg -c '^\[\[shapes\]\]' slides/cover.toml   # 2 个 placeholder
rg -c '^\[\[shapes\]\]' slides/end.toml     # 0 个形状
```

`gwen build` 已拦截 TOML 语法、未知字段、样式引用和类型错误，不要重复检查。机械检查只兜住 gwen 不管的文案与几何约定；项目多了再写脚本，别为几条 `rg` 建 `scripts/`。
